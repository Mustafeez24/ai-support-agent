# AI Support Agent — AmazonHelp

An AI customer-support agent for **AmazonHelp**, built on the Kaggle
*Customer Support on Twitter* dataset. Given a customer message, it:

1. **Classifies** the message into one of 11 intents discovered from
   AmazonHelp's own historical conversations (`config/intents.yaml`).
2. **Retrieves** how AmazonHelp actually resolved similar issues before
   (local, free embeddings + FAISS — no paid retrieval API).
3. **Drafts a reply** grounded only in that retrieved evidence (NVIDIA
   `nemotron-3-ultra-550b-a55b`) — it is instructed never to invent
   policies, refunds, prices, dates, or account actions.
4. **Decides** AUTO_HANDLE vs. ESCALATE_TO_HUMAN with a stated,
   rule-based reason.

The system is compared against two required baselines (a trivial
majority/always-escalate baseline, and a non-LLM TF-IDF baseline) and
evaluated against a hand-labeled golden set, with an LLM judge whose
agreement with real human ratings is measured, not assumed. See
`report/report.md` for full methodology and results, and `DECISIONS.md`
for the rationale behind every non-obvious engineering choice.

**The raw dataset (`data/raw/twcs.csv`, ~517MB / ~2.8M rows) is never
committed to this repository** — it's gitignored; you place it locally
(instructions below), and every derived artifact regenerates from it.

## Status

The full pipeline is implemented and unit-tested (89 tests, all passing,
`python -m pytest`). It was built and tested against a synthetic fixture
CSV (`tests/fixtures/sample_twcs.csv`) because the real dataset wasn't
available while writing this code. **Dataset-derived numbers (brand
statistics, taxonomy validation, evaluation results, failure examples) do
not exist yet in this repo** — `report/report.md` marks each one PENDING
with the exact command that produces it. Running that command sequence on
your machine, with the real CSV in place, is what turns PENDING into real
numbers.

## Architecture

```
customer message
    -> intent classification   (src/intents/classifier.py: TF-IDF + LogisticRegression)
    -> retrieval                (src/retrieval/retriever.py: FAISS over sentence-transformer embeddings)
    -> escalation decision      (src/agent/escalation.py: deterministic rule policy)
    -> reply generation         (src/agent/prompts.py + src/llm/nvidia.py, grounded in evidence,
                                  skipped if the decision is already ESCALATE_TO_HUMAN)
    -> structured result        {intent, intent_confidence, reply, decision, escalation_reason, evidence}
```

## Setup

**Python 3.11+** required (developed against 3.11.15; reasonable effort
made for 3.13 compatibility per pinned dependency ranges in
`requirements.txt`).

### 1. Clone and install (Windows)

```powershell
git clone <this-repo-url>
cd ai-support-agent
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

### 1. Clone and install (macOS/Linux)

```bash
git clone <this-repo-url>
cd ai-support-agent
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

`sentence-transformers` pulls in PyTorch (CPU); the install can take a
few minutes and a few hundred MB on first run.

### 2. Configure `.env`

```powershell
copy .env.example .env
```
```bash
cp .env.example .env
```
Edit `.env` and set a real `NVIDIA_API_KEY` (get one from
[build.nvidia.com](https://build.nvidia.com)). `NVIDIA_BASE_URL` and
`NVIDIA_MODEL` already default to the right values. **Without a real key,
reply generation and the LLM judge fail gracefully** (a clear
`LLMNotConfiguredError`, and the agent escalates to a human instead of
crashing or sending a broken reply) — everything else (data pipeline,
intent classification, retrieval, baselines, non-LLM metrics) still runs.

`.env` is gitignored; never commit it.

### 3. Place the dataset

Download the *Customer Support on Twitter* dataset (Kaggle:
`thoughtvector/customer-support-on-twitter`) and place it at:

```
data\raw\twcs.csv      (Windows)
data/raw/twcs.csv      (macOS/Linux)
```

This file is **not** included or downloaded automatically, and is
gitignored — it never gets committed.

## Running the Pipeline

Run these in order. Each stage caches its output, so re-running an
earlier stage doesn't force-repeat later ones unless its output changed.

```powershell
# 1. Dataset analysis (schema, stats, candidate-brand ranking)
python scripts\analyze_dataset.py
# -> outputs\analysis\{dataset_summary.json, brand_statistics.csv, candidate_brands.md}

# 2. Preprocessing (thread reconstruction, cleaning, train/golden split)
python scripts\preprocess.py
# -> data\processed\amazonhelp_{full,resolution_pairs}.parquet

# 3. Intent discovery (validate config\intents.yaml against real clusters)
python -m src.intents.discover
# -> outputs\analysis\intent_clusters_report.json
# Review it, then edit config\intents.yaml (see the file's own header for
# instructions), replacing the current 2 seed examples/intent with more
# real ones -- this materially improves step 5's weak-label quality
# (see DECISIONS.md #20).

# 4. Golden evaluation set
python scripts\build_golden_set.py sample
python scripts\build_golden_set.py label
# interactive -- a real person labels ~200 examples; safe to Ctrl-C and resume
python scripts\build_golden_set.py report
# -> data\golden\{golden_set_candidates.csv, golden_set.csv, label_distribution.json}

# 5. Train the production intent classifier (weak-label bootstrap, see DECISIONS.md #20)
python scripts\train_classifier.py
# -> outputs\cache\intent_classifier.joblib

# 6. Build the retrieval index
python scripts\build_index.py
# -> outputs\cache\faiss_index\

# 7. Evaluate: production agent + both baselines vs. the golden set
python scripts\evaluate.py run
# -> outputs\metrics\{comparison_table.csv, evaluation_report.json, judge_scores.csv}

# 8. Human-vs-judge agreement (requires a real person)
python scripts\evaluate.py human-review-template
# a human fills in outputs\metrics\human_review_template.csv (scores 1-5,
# no_hallucination True/False), saves it as
# outputs\metrics\human_review_ratings.csv
python scripts\evaluate.py agreement
# -> outputs\metrics\judge_agreement_report.json
```

macOS/Linux: same commands with `/` paths and `python3`, e.g.
`python3 scripts/preprocess.py`.

### Running the agent on a single message

```powershell
python scripts\run_agent.py --message "My Amazon order has not arrived yet"
```
or equivalently:
```powershell
python -m src.agent.agent --message "My package is late"
```
Add `--json` for machine-readable output. Requires steps 2, 5, and 6
above to have been run first (it loads the trained classifier and FAISS
index); it will tell you exactly which script to run if one is missing.

**Sample output** (illustrative shape — see report.md Section 10 for real
numbers once available):
```
Intent:     delivery_delay (confidence=0.87)
Decision:   AUTO_HANDLE
Reason:     Intent classified with sufficient confidence and grounded in consistent historical evidence.
Reply:      We're sorry for the delay! We've located your order and it's on its way -- you should receive tracking shortly.
Evidence:
  1. [0.81] customer: 'My order still has not arrived, its been a week'
     -> reply: '@customer Sorry about that! Checking on this now, please DM your order number.'
  2. [0.77] customer: 'when will my late package finally arrive'
     -> reply: '@customer We've flagged this with our carrier and it should arrive within 2 days.'
```

## Baseline Comparison

- **Baseline 1 (trivial):** majority-intent classifier + a fixed generic
  reply + always-escalate policy. The floor.
- **Baseline 2 (simple, non-LLM):** the *same* TF-IDF+LogisticRegression
  classifier and *same* rule-based escalation policy as production, but
  TF-IDF nearest-neighbor retrieval and a verbatim top-1 historical reply
  instead of dense retrieval + LLM generation. Deliberately shares two of
  the three production components so the comparison isolates what dense
  retrieval and generation specifically add (`DECISIONS.md` #23).

Run `python scripts/evaluate.py run` to produce
`outputs/metrics/comparison_table.csv` with all three side by side.

## Expected Runtime

Rough estimates on a typical laptop CPU (no GPU required anywhere):

| Step | Full dataset (~2.8M rows) | Fast dev run (`DATA_SAMPLE_SIZE=100000`) |
|---|---|---|
| `analyze_dataset.py` | 3-8 min (two streaming passes) | < 1 min |
| `preprocess.py` | 3-8 min | < 1 min |
| `train_classifier.py` | 1-3 min | < 30 sec |
| `build_index.py` (embeds all train_retrieval messages) | 10-30 min (CPU-bound, depends on corpus size after filtering) | 1-2 min |
| `evaluate.py run` (~200 golden examples through 3 systems + LLM judge) | 5-15 min (network-bound: NVIDIA API latency) | same (golden set size doesn't shrink with `DATA_SAMPLE_SIZE`) |
| Golden-set labeling | unbounded (human-paced; ~200 examples, budget 1-3 hours) | same |

For a **fast, code-level smoke test** (not real headline numbers), set
`DATA_SAMPLE_SIZE=100000` in `.env` before running steps 1-2 and 5-6 above
— everything downstream still runs correctly, just on less data.
Reproducing real, reportable headline numbers requires the full dataset
and a real (unbounded, human-paced) golden-set labeling session; it is not
a 15-minute process end-to-end, and `report/report.md` does not claim
otherwise.

## Limitations

See `report/report.md` Sections 12 and 14 for the full, honest list
(small golden set, sampling bias, class imbalance, judge bias, retrieval
leakage risk mitigated but not provably zero, imperfect historical
responses, offline-vs-production gap, judge-is-not-ground-truth). In
short: this is a rigorously *evaluated* system, not a claim of a
production-ready one.
